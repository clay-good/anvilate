# Change: Drive trains — a gearbox that is checked as a machine, not as a pile of passing parts

## Why

Anvilate already screens every part of a gearbox one at a time: a spur gear mesh
(bending and contact), a shaft (yield, DE-Goodman fatigue, windup), a key, a rolling
bearing. `add-product-structure` lists a two-stage reducer as a worked product, and
`add-product-screening` carries loads to ground by statics. What none of them knows is
that the reducer **moves**, and that is where a gearbox is actually wrong:

- **The loads come from the motion.** The torque on the second-stage pinion is the input
  torque times the first-stage ratio, less the first mesh's losses. Today the agent types
  that torque into each mesh by hand, and a typo there is invisible because each mesh still
  passes on the number it was given.
- **The gears load the shafts, and the shafts load the bearings.** The tangential and
  radial forces at each mesh set the bending in each shaft and the reaction at each
  bearing. Each screen exists. Nothing connects them, so a bearing is rated against a load
  someone estimated.
- **Geometry has to close.** In a reverted (in-line) reducer both stages must share one
  center distance; tooth counts must give the required output speed within its band;
  the gear blanks must clear the housing and each other while they turn. None of this is
  a part check.
- **Heat is a rating too.** A reducer that passes every strength check can still run its
  oil past its limit. Gear-unit standards treat thermal capacity as a rating in its own
  right (ISO/TR 14179-1).

This is also where AI tools visibly fail. An ICML 2026 benchmark found agents could build
a right-angle gearbox that looked right in most attempts, and scored about 4% on its
functional checks. A gearbox Anvilate produces should come with the functional checks
already run.

## What Changes

| Area | Change |
| --- | --- |
| Drive-train declaration | A product may declare a drive train over its items: which shafts carry which gears, couplings and bearings; which gears mesh; the input (power and speed, or torque and speed) and the required output (a speed band, a torque, a life). |
| Speed and torque flow | Every shaft's speed, torque and power is derived from the input through each mesh's ratio and a declared, cited efficiency. A required output speed band is a check. The agent never types a mesh torque again. |
| Kinematic consistency | The gear graph must determine every shaft's speed exactly once. Parallel paths that disagree, a reverted layout whose stages do not share a center distance, or a mesh whose center distance does not match its gears' pitch radii are refused before anything is built. |
| Gear geometry checks | Per mesh: contact ratio, undercut and minimum teeth, tip thickness, center distance, and backlash, in ISO 21771-1 terms. The rating screens refuse inputs outside the method's stated validity range, so they never extrapolate. |
| Gear forces to bearings | Tangential, radial and (for helical gears) axial mesh forces are applied to each shaft. Each two-bearing shaft is solved by statics for its bearing reactions and bending moments. A shaft with more supports is named as indeterminate, never solved by a guessed split. |
| Downstream screens fed | The existing mesh, shaft, key and bearing screens run on the derived loads, each entry depending on the flow entry it read. Bearing life is held against the required life. |
| Shaft deflection and slope | Deflection and slope at each gear and bearing, against limits the document declares or a cited textbook table supplies. |
| Thermal capacity | The heat generated by mesh and bearing losses against the housing's dissipation over a declared ambient. The result is the steady oil temperature against its declared limit. The method stays not evaluated until the standard's text has been read and the method anchored. |
| Motion clearance | Each rotating item sweeps its envelope of revolution. Clearance is checked between swept envelopes and stationary items, and between swept envelopes on different shafts. |
| Gear data table | Each gear's data block (module, teeth, pressure and helix angle, profile shift, basic rack, accuracy class, test dimension) is written with the drawing and the release package. Anvilate defines the fields, because ISO 1340, the old standard for this block, is withdrawn. |

## Impact

- New capability: `drive-trains`.
- Builds on: `add-product-structure` (items and paths), `add-interface-contracts` (a
  shaft-in-bore and a gear-on-shaft are interfaces), `add-purchased-components` (motors and
  bearings as records with ratings), `add-product-screening` (load path, swept clearance,
  mass roll-up), and the existing machinery pack (mesh, shaft, key and bearing screens,
  reused, not rewritten).
- Feeds: `add-local-fea` (housing loads are the bearing reactions derived here) and
  `add-design-optimization` (the reducer's variables and checks).
- Reference implementations of gear rating exist only under GPL or LGPL licenses, so
  nothing is vendored. Methods are implemented from the cited standards and textbooks.
- Explicitly out:
  - True involute tooth solids. Gears stay envelopes until `expand-drawable-parts` draws
    them.
  - Dynamics: transmission error, gear rattle, run-up, and transient simulation.
  - Planetary, bevel and worm stages in the first phase (worm screening exists for single
    meshes).
  - Lubricant selection.
  - A mobility verdict from the Grübler–Kutzbach count. Gear trains are overconstrained,
    and the count misreads them, so consistency of the speed graph is the check instead.
