# Repair levers: what a failing check on each screen tells the caller to move.
#
# A scorecard that says only "this failed" leaves the caller searching. A repair lever
# names the parameter to move and the direction that improves the margin, and where a
# design inverse exists it names the value that lands the required margin exactly
# (docs/repair-feedback.md). This file records the decision for EVERY public screen, so
# that a screen with no lever is a recorded gap rather than an oversight.
#
# Format: "<module>.<screen> -> <parameter> (solved|directional)" for a screen that emits
# a lever, one line per lever; a bare "<module>.<screen>" for one that emits none yet. A
# screen may appear more than once under `levers` and never in both sections.
#
# THE GATE READS BOTH DIRECTIONS (tests/test_contract.py). Every public screen must appear;
# every recorded lever must actually be constructed by that screen — resolved through the
# module's own call graph, because the hint is usually built in a helper the screen calls;
# every lever a screen constructs must be recorded; and a lever's parameter must be a
# keyword argument of the screen or a field of a model it takes, or it names something the
# caller cannot move.
#
# AN AGGREGATOR'S LEVERS ARE ITS ELEMENTS'. `screening.screen_spec` — the library's
# front door, the function `anvilate check` runs — dispatches each declared element
# through a registry and returns their entries, hints and all. It is recorded here as
# having no lever of its OWN, which is what the gate can resolve: the walk follows a
# module's own call graph, and the registry hands back a callable rather than naming one.
# A card from it carries whatever the element screens carry, and the four rows for
# `screen_structure` are the same thing where the dispatch IS in one module and so
# resolves.
#
# WHY THE OTHERS HAVE NONE. Three kinds, and knowing which one a screen is in is most of
# deciding whether it will ever get a lever:
#
#   1. The demand and the allowable are both the CALLER'S, computed upstream. This is
#      almost all of them: `stress.strength_scorecard`, `beam.deflection_scorecard`, the
#      three fatigue criteria, the four NDS timber checks, the DSM and FAD screens, the
#      BTH-1 members, and the three pressure-vessel screens — which take a reinforcement
#      area or a flange stress already worked out and judge it. A stress is not a knob; the
#      geometry that produced it is, and these screens never saw it.
#   2. Aggregators — `screening.screen_spec`, `screen_structure_element`,
#      `screen_lifter_device`, `callouts.callout_scorecard`. Their cards carry whatever
#      their elements carry; see the note above. And `loads.combination_scorecard`, where
#      the lever is the design loads themselves.
#   3. A geometry whose knob is not a number: `screen_beam_member` and
#      `screen_beam_column`, whose section is a discrete choice from a table. A corrective
#      value is a float, and "a bigger section" is not one.
#
# THIS LIST WAS WRONG WHEN IT WAS FIRST WRITTEN, in five of its six hardest cases, and it
# is worth saying why. It was written from the screens' NAMES: the concrete bearing, the
# bolted connection and the column member were filed as "no single knob" and all three
# turned out to have one (two regimes that each solve; three knobs, one per check; a
# direction with no closed inverse), and the three pressure-vessel screens were filed
# there when they belong under 1. Read the signature.

# A THIRD KIND, `aggregated`, for a screen that FORWARDS a lever rather than computing
# one. `screen_structure` dispatches each member and concatenates their entries, so its ten
# rows are its members', arriving unchanged. They are recorded because a reader of that
# card gets them, and they are labelled because the value sweep in tests/test_contract.py
# would otherwise demand a test that notices a wrong value there — and the value is the
# member screen's to be wrong about. An `aggregated` row has to name a parameter some other
# screen offers, or the label is a way of ducking the sweep.
#
# `solved` and `directional` are not interchangeable. A solved lever claims a value; a
# directional one claims only a sign, which is a claim about the check's shape over its
# whole domain and has to be swept before it is declared. `screen_infinite_slope` carries
# both, and its slope-angle direction is scoped to below 45 degrees because the trend
# reverses above it.
